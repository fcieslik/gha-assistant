# Agent recenzujący: review wg intencji i wg kodu

Status: ready-for-agent

## Problem Statement

Graf ma dziś stubowy węzeł `run_agent`, który nic nie recenzuje. Chcę, żeby agent robił prawdziwe review PR, ale pojedyncze "przeczytaj diff i napisz uwagi" nie wystarcza z trzech powodów. Po pierwsze, review powinno odpowiadać na dwa różne pytania: czy kod robi to, co obiecuje Spec, Ticket i ADR dołączone do PR (zgodność z Intent), oraz czy sam kod jest dobry (błędy, bezpieczeństwo). Po drugie, uwagi generowane przez model często zawierają fałszywe alarmy i zmyślone ścieżki lub linie, a taki Review traci zaufanie i Pull Request Reviews API odrzuca nieistniejące pozycje. Po trzecie, PR i jego pliki to dane niezaufane, więc nic, co model przeczyta, nie może nim sterować ani dawać mu uprawnień do zapisu.

Dodatkowo to projekt do nauki LangGraph. Chcę zbudować ten fragment tak, żeby ćwiczył reducery, `Send` (map-reduce), conditional edges i `RetryPolicy`, a nie ukrywał całej orkiestracji w jednym wywołaniu SDK.

## Solution

`run_agent` zostaje zastąpiony płaskim przepływem w grafie głównym, z kilkoma Agentami o wąskich rolach:

1. **Dwóch recenzentów równolegle.** `review_code` ocenia jakość kodu, osobno dla każdego pliku z `change["code"]` (`Send`). `review_intent` ocenia zgodność zmiany z Intent files (raz na PR, tylko gdy PR je zawiera). Obaj zwracają Findings w tym samym kształcie.
2. **`validate_findings`** (zwykły kod, bez modelu) odrzuca Findings wskazujące nieistniejący plik lub linię, z cytatem, którego w kodzie nie ma, albo recenzujące spec bez odwołania do spec.
3. **`verify_finding`**: model Sonnet sprawdza każdy Finding osobno (`Send`), z dostępem tylko do odczytu, i zwraca werdykt `confirmed`, `refuted` lub `inconclusive`.
4. **`judge_findings`**: model Sonnet, bez narzędzi, dostaje Findings razem z werdyktami oraz zasady. Zwraca decyzje po `id` (zostaw, odrzuć, scal) i podsumowanie. Kod stosuje decyzje do oryginalnych obiektów, więc sędzia nie może dopisać Findingu ani zmienić miejsca w kodzie.
5. `publish` dostaje końcowe Findings i `summary` i zostawia w PR komentarz ze statusem i podsumowaniem, także gdy nie ma żadnej uwagi. Komentarze przy liniach (Pull Request Reviews API) to osobna specyfikacja.

Dostarczamy to cienkimi, kolejnymi krokami. Pierwszy krok to wyjście bez kodu do recenzji (`Command` w `collect_input` i node `nothing_to_review`), drugi to komentarz w PR ze statusem, żeby run nigdy nie kończył się zielono bez śladu, trzeci to sam szkielet grafu z pustymi nodami, w którym sprawdzamy topologię, zanim pojawi się jakikolwiek model. Każdy kolejny krok zamienia jeden pusty node na prawdziwy, a graf przez cały czas działa od START do END.

## User Stories

1. Jako autor PR, chcę, żeby kod każdego zmienionego pliku był oceniony pod kątem błędów i bezpieczeństwa, aby dostać uwagi, których sam bym nie zauważył.
2. Jako autor PR, chcę, żeby agent sprawdził zmianę względem Spec, Ticketów i ADR dołączonych do PR, aby wiedzieć, czy zrobiłem to, co zapisałem.
3. Jako autor PR, chcę, żeby niezrealizowane kryterium z Ticketu pojawiło się w podsumowaniu nawet wtedy, gdy nie da się go przypisać do żadnej linii, aby nie przeoczyć brakującej pracy.
4. Jako autor PR, chcę, żeby uwaga o kodzie wskazywała plik i linię mojej zmiany, aby od razu wiedzieć, gdzie patrzeć.
5. Jako autor PR, chcę, żeby uwaga zawierała cytat z kodu, aby bez otwierania pliku zrozumieć, której linii dotyczy.
6. Jako autor PR, chcę, żeby każda uwaga miała wagę (low, medium, high), aby wiedzieć, co poprawić najpierw.
7. Jako autor PR, chcę, żeby uwaga zawierała sugestię poprawki, aby nie musieć jej wymyślać.
8. Jako autor PR, chcę, żeby uwaga o niezgodności ze Spec wskazywała, które kryterium i z którego pliku narusza, aby móc je sprawdzić.
9. Jako autor PR, chcę, żeby agent nie zgłaszał plików i linii, których nie ma w mojej zmianie, aby nie tracić czasu na uwagi o zmyślonym kodzie.
10. Jako autor PR, chcę, żeby uwaga była najpierw zweryfikowana w kodzie przez osobny krok, aby fałszywe alarmy nie trafiały do mojego PR.
11. Jako autor PR, chcę, żeby ta sama uwaga zgłoszona dwa razy została scalona w jedną, aby nie czytać duplikatów.
12. Jako autor PR, chcę, żeby review miało ograniczoną liczbę uwag, uporządkowanych od najważniejszych, aby nie utonąć w szumie.
13. Jako autor PR bez żadnego pliku Spec, Ticket ani ADR, chcę, żeby agent zrecenzował sam kod i nie zmyślał uwag o zgodności z intencją, aby brak dokumentów nie psuł review.
14. Jako autor PR, którego jedyną intencją jest tytuł i opis, chcę, żeby agent nie próbował oceniać zgodności ze spec, aby nie dostawać domysłów.
15. Jako autor PR, chcę, żeby pliki usunięte, lockfile'e, binaria i dokumentacja nie były recenzowane jako kod (już obsłużone przez Change), aby review dotyczyło tylko kodu.
16. Jako autor PR, chcę, żeby pliki były recenzowane równolegle, aby duże PR mieściły się w limicie czasu runnera.
17. Jako autor PR, chcę, żeby awaria recenzji jednego pliku nie kasowała uwag o pozostałych, a podsumowanie mówiło, czego nie sprawdzono, aby dostać częściowe, uczciwe review.
18. Jako autor PR, chcę, żeby awaria sędziego nie anulowała całego review, aby i tak dostać uwagi posortowane wg wagi z adnotacją o awarii.
19. Jako autor PR, chcę, żeby mój kod i opis PR nie mogły wydawać poleceń agentowi, aby review nie dało się podmienić przez treść PR.
20. Jako autor repozytorium, chcę, żeby agent miał tylko narzędzia do odczytu, aby nic w repozytorium nie zostało zmienione ani wykonane.
21. Jako autor repozytorium, chcę, żeby tani model (Haiku) robił recenzje, a Sonnet weryfikacje i jedno podsumowanie, aby koszt jednego review był przewidywalny.
22. Jako autor repozytorium, chcę, żeby liczba równoległych wywołań modelu była ograniczona, aby nie przekraczać limitów API przy dużym PR.
23. Jako autor repozytorium, chcę, żeby każde wywołanie modelu miało timeout, aby zawieszony Agent nie zużywał całego `timeout-minutes`.
24. Jako autor repozytorium, chcę, żeby przejściowe błędy API (429, 5xx) były ponawiane, a trwałe (zły klucz) nie, aby nie palić czasu i pieniędzy na niewykonalne próby.
25. Jako autor repozytorium, chcę, żeby ten sam agent działał we wszystkich repozytoriach bez konfiguracji per repozytorium, aby nie utrzymywać reguł w wielu miejscach.
26. Jako deweloper agenta, chcę, żeby pierwszym krokiem był szkielet grafu z pustymi nodami, aby zweryfikować topologię (fan-out, fan-in, routing, reducery) bez modelu i bez kosztów.
27. Jako deweloper agenta, chcę, żeby każdy kolejny krok zamieniał jeden pusty node na prawdziwy i zostawiał graf uruchamialny end-to-end, aby zawsze było co przetestować.
28. Jako deweloper agenta, chcę, żeby pusty node zwracał stały, deterministyczny wynik, aby topologię dało się obserwować w testach.
29. Jako deweloper agenta, chcę, żeby cały dostęp do Claude Agent SDK przechodził przez jedną granicę, aby testy podmieniały jedno miejsce.
30. Jako deweloper agenta, chcę, żeby testy grafu nie wołały prawdziwego modelu, aby były szybkie, tanie i deterministyczne.
31. Jako deweloper agenta, chcę, żeby Finding miał jeden typowany kształt używany przez wszystkich recenzentów, aby kolejne węzły nie musiały zgadywać formatu.
32. Jako deweloper agenta, chcę, żeby `id` i `source` Findingu nadawał kod, a nie model, aby model nie mógł ich pomylić ani sfałszować.
33. Jako deweloper agenta, chcę, żeby sędzia zwracał decyzje po `id`, a nie nowe obiekty, aby nie mógł zmienić miejsca w kodzie ani dopisać Findingu.
34. Jako deweloper agenta, chcę, żeby zasady sędziego były stałą w kodzie, a nie czymś z PR, aby ich nie dało się podmienić przez zmianę.
35. Jako deweloper agenta, chcę, żeby walidacja Findings była czystą funkcją na danych, aby testować ją tabelą przypadków bez grafu.
36. Jako deweloper agenta, chcę, żeby wyniki równoległych nodów łączyły się reducerem, a nie nadpisywały, aby żaden recenzent nie gubił cudzych uwag.
37. Jako deweloper agenta, chcę, żeby testy mogły sprawdzić, które nody i ile razy się wykonały (`stream_mode="updates"`), aby asercje dotyczyły zachowania, a nie wywołań wewnętrznych.
38. Jako deweloper agenta, chcę, żeby modele dla ról (recenzent, weryfikator, sędzia) były stałymi w jednym miejscu, aby zmiana modelu była jedną zmianą.
39. Jako deweloper agenta, chcę, żeby dokumentacja projektu opisywała nowy układ grafu i zamknęła otwartą decyzję o roli SDK, aby `PROJECT_GOAL.md` nie kłamał.
40. Jako deweloper agenta, chcę opcjonalnego testu z prawdziwym modelem, pomijanego bez klucza, aby raz sprawdzić integrację, nie obciążając zwykłego `pytest`.
41. Jako autor PR, chcę, żeby chwilowy błąd API przy jednym pliku ponowił tylko ten plik, a nie całe review, aby nie płacić drugi raz za to, co już się udało.
42. Jako autor PR, chcę, żeby weryfikacja Findingu, która nie zdołała się wykonać, nie usuwała tego Findingu, tylko oznaczała go jako niezweryfikowany, aby prawdziwa uwaga nie ginęła przez awarię sieci.
43. Jako autor repozytorium, chcę, żeby ponawianie miało odstępy z losowym rozrzutem, aby równoległe wywołania nie uderzały w API w tym samym momencie po błędzie 429.
44. Jako autor repozytorium, chcę, żeby suma ponowień nigdy nie przekraczała limitu czasu runnera, aby retry nie zamieniał się w przekroczenie `timeout-minutes`.
45. Jako deweloper agenta, chcę, żeby jedno miejsce klasyfikowało błąd Agenta jako przejściowy lub trwały, aby wszystkie nody ponawiały według tej samej reguły.
46. Jako deweloper agenta, chcę, żeby testy retry działały bez realnego czekania, aby sprawdzać strategię w milisekundach.
47. Jako autor PR zmieniającego tylko dokumentację lub lockfile, chcę, żeby run kończył się czytelnym komunikatem w logu Actions i w PR, że nie ma czego sprawdzać, aby było jasne, że agent nie zawiódł, tylko nie miał pracy.
48. Jako deweloper agenta, chcę, żeby wyjście "nic do recenzji" było osobnym, nazwanym node, aby w `stream_mode="updates"` i na rysunku grafu było widać, że run skończył się świadomie.
49. Jako deweloper agenta, chcę, żeby decyzja "jest co recenzować" była w jednym miejscu, aby node i krawędź nie rozjechały się ze sobą.
50. Jako autor repozytorium, chcę, żeby ścieżka bez kodu nie wykonywała żadnego node z modelem, aby nie płacić za puste review.
51. Jako autor PR, chcę, żeby po każdym runie w PR był widoczny komentarz ze statusem (co sprawdzono albo dlaczego nic), aby nie zastanawiać się, czy zielony run przeszedł prawidłowo.
52. Jako autor PR bez żadnych uwag, chcę komentarza "brak uwag" z liczbą sprawdzonych plików, aby cisza nie wyglądała jak awaria agenta.
53. Jako autor PR, chcę, żeby kolejny push nadpisywał poprzedni komentarz agenta zamiast dokładać nowy, aby PR nie zapełniał się statusami.
54. Jako autor PR, chcę, żeby komentarz podawał commit i czas, których dotyczy, aby wiedzieć, czy nie jest nieaktualny.
55. Jako autor repozytorium, chcę, żeby ponowienie publikacji po timeoucie nie dublowało komentarza, aby retry był bezpieczny.
56. Jako deweloper agenta, chcę trybu `dry_run`, w którym komentarz jest drukowany zamiast wysyłany, aby sprawdzać treść lokalnie bez dostępu do GitHuba.
57. Jako autor repozytorium, chcę, żeby brak tokenu lub celu publikacji kończył run błędem, a nie cichym pominięciem, aby zielony run zawsze oznaczał, że komentarz powstał.

## Implementation Decisions

- **Topologia: płaska, bez subgraphów.** Węzeł `run_agent` znika. `collect_input` zwraca `Command` i jest jedynym routerem wyjścia z pierwszego kroku: gdy `change["code"]` jest puste, `goto` kieruje do `nothing_to_review` (patrz niżej), w przeciwnym razie `goto` zawiera fan-out: `review_code` uruchamiany `Send` raz na plik z `change["code"]`, oraz `review_intent` raz, tylko gdy `change["intent"]` jest niepuste. Obie gałęzie wpadają do `validate_findings`. Po nim routing: brak Findings oznacza przejście wprost do `publish`; w przeciwnym razie `verify_finding` uruchamiany `Send` raz na Finding, potem `judge_findings`, potem `publish`. Subgraphy i subagenci SDK są świadomie pominięte (kontrakt nauki: LangGraph orkiestruje, SDK jest jednym wywołaniem w nodzie).
- **Wyjście bez kodu do recenzji: `Command` i `nothing_to_review`.** Gdy `change["code"]` jest puste, `collect_input` zwraca `Command` z `update` niosącym `change` i `goto` do nowego, ostatniego node `nothing_to_review`. Ten node wypisuje informację, że nie ma czego sprawdzać (z liczbą plików ignorowanych i Intent files, żeby było widać dlaczego) i zostawia ją w PR jako komentarz ze statusem (patrz "Komentarz w PR"), nie zmienia stanu i prowadzi do END. W ścieżce z kodem `collect_input` także zwraca `Command` (z `update` niosącym `change`), a `goto` wskazuje następny krok. `Command` i krawędź warunkowa z tego samego node wykonują się oba (`goto` nie wyłącza krawędzi), dlatego dotychczasowa krawędź warunkowa po `collect_input` jest usuwana, a cała decyzja o wyjściu żyje w jednym miejscu: w czystej funkcji wybierającej cel na podstawie `change`. Typ zwrotny node deklaruje możliwe cele (`Command[Literal[...]]`), żeby graf znał krawędzie i dał się narysować. Błędy wejścia (`ValueError` o braku `base_ref` lub `repo_path`) nadal są wyjątkiem, nie przekierowaniem, a `RetryPolicy` na `collect_input` zostaje bez zmian. Konsekwencja: `collect_input` zna nazwy nodów, do których kieruje.
- **Granica wykonania Agenta: jeden serwis.** Jeden moduł (`agent.py`), jedyne miejsce importujące Claude Agent SDK, z jedną funkcją `run_agent`. Parametry per wywołanie: `model`, `system_prompt`, `prompt` (dane), `output_schema`, opcjonalnie `max_turns` i `tools` (sędzia dostaje `[]`). Wspólne, wymuszone domyślne: `max_turns=30`; narzędzia tylko `Read`, `Glob`, `Grep`; `cwd` to katalog uruchomienia; `fallback_model` Sonnet 5.5 (pomijany, gdy `model` już nim jest); `setting_sources=[]`, czyli nic z repozytorium PR (CLAUDE.md, `.claude/`) nie jest ładowane. Zwraca sparsowany structured output; jego brak to wyjątek `InvalidAgentOutput`. Timeout i retry nie są w serwisie, tylko na nodzie (`add_node(timeout=..., retry_policy=...)`). Nie ma własnej hierarchii wyjątków: klasyfikację przejściowy/trwały robi jeden predykat `is_transient_agent_error` w tym samym module. Wszystkie nody z modelem korzystają wyłącznie z serwisu. To rozstrzyga otwartą decyzję nr 3 z `PROJECT_GOAL.md`: węzeł grafu to jedno wywołanie Agenta ze structured output, pętlę narzędzi prowadzi SDK, LangGraph nie dokłada własnej pętli ReAct.
- **Finding (jeden kształt dla wszystkich).** Pola: `id` (nadaje kod), `source` (`spec` lub `code`, ustawia node, nie model), `severity` (`low`, `medium`, `high`), `message`, `file` (może być brak), `line` (może być brak), `evidence` (dosłowny cytat z kodu, może być brak), `suggestion` (może być brak), `spec_ref` (plik Intent i kryterium, wymagane gdy `source` to `spec`, w pozostałych przypadkach brak). Finding bez `file` i `line` to uwaga ogólna (np. niezrealizowane kryterium); trafia do podsumowania, nie do komentarza przy linii. Model zwraca Finding bez `id` i `source`. To rozszerza definicję z `CONTEXT.md` (plik, linia, waga, treść, sugestia).
- **Stan.** `ReviewState` zyskuje pola etapów: kandydaci od recenzentów (reducer łączący listy), zwalidowane Findings, werdykty weryfikatorów (reducer łączący listy), końcowe Findings, ostrzeżenia o degradacji (reducer łączący listy). Dotychczasowe `summary` zostaje i ustawia je sędzia. Workerzy `Send` dostają prywatny, wąski payload (ścieżka pliku lub jeden Finding), nie cały stan.
- **Zachowanie `Send` przy pustej liście.** Krawędź warunkowa zwracająca pustą listę `Send` kończy gałąź i nic dalej się nie wykona. Dlatego puste Findings po walidacji są obsługiwane jawnym routingiem do `publish`, a nie pustym fan-outem.
- **Fan-in bez bariery listowej.** Recenzenci wpadają do `validate_findings` osobnymi krawędziami, nie jedną krawędzią z listą źródeł, bo `review_intent` bywa pominięty i bariera czekałaby na niego bez końca. Wszyscy recenzenci działają w tym samym kroku grafu, więc `validate_findings` wykonuje się raz po wszystkich. Zachowanie weryfikuje test topologii z kroku ze szkieletem grafu (03).
- **`review_code`.** Jedno wywołanie na plik. Ocenia kod sam w sobie (błędy, bezpieczeństwo, ryzykowne wzorce). Zgodność z intencją to zadanie `review_intent`, więc workerzy per plik nie dostają treści Intent files. Diff pliku dostaje w prompcie jako dane (agent nie ma `Bash`, więc nie woła gita), a potrzebny kontekst doczytuje narzędziami tylko do odczytu. Ustawia `source` na `code`.
- **`review_intent`.** Jedno wywołanie (dwuetapowe, prompt chaining) na PR. Etap 1 wyciąga z Intent files listę kryteriów z odwołaniem do pliku. Etap 2 sprawdza każde kryterium względem zmiany. Raportuje: kryterium niezrealizowane (uwaga ogólna), implementację sprzeczną ze Spec lub ADR (zakotwiczoną, gdy się da), zmianę spoza deklarowanego zakresu. Treść Intent files czyta narzędziem, nie jest trzymana w stanie. Tytuł i opis PR są kontekstem o najniższym priorytecie i same nie uruchamiają tego noda. Ustawia `source` na `spec` i wymaga `spec_ref`.
- **`validate_findings`.** Czysta funkcja bez modelu. Odrzuca Finding, gdy: plik nie należy do `change["code"]`, linia wykracza poza plik, `evidence` nie występuje w wskazanej linii, brak `spec_ref` przy `source` równym `spec`. Usuwa dokładne duplikaty (ten sam plik, linia i źródło). Powód odrzucenia trafia do ostrzeżeń, żeby dało się go zobaczyć w podsumowaniu lub logu.
- **`verify_finding`.** Jedno wywołanie na Finding, Sonnet, tylko narzędzia do odczytu. Zwraca `confirmed`, `refuted` lub `inconclusive` z krótkim uzasadnieniem. Liczba weryfikacji jest ograniczona stałą (propozycja: 20, najwyższe wagi pierwsze); pozostałe Findings przechodzą do sędziego jako niezweryfikowane.
- **`judge_findings`.** Sonnet, bez narzędzi (`tools=[]`). Dostaje Findings i werdykty jako dane (blok danych), a zasady w prompcie systemowym. Zwraca listę decyzji (`id`, `verdict`: zostaw, odrzuć lub scal, `merge_into`, `severity`, `reason`) oraz `summary`. Kod stosuje decyzje do oryginałów. Zasady (stała w kodzie): odrzucaj `refuted`; scalaj duplikaty semantyczne; waga ma wynikać z wpływu, nie ze stylu; uwagi czysto stylistyczne odrzucaj; nie dopisuj nowych Findings; limit uwag w Review (propozycja: 15).
- **Modele.** Recenzenci (`review_code`, `review_intent`): Haiku 5.5. Weryfikator (`verify_finding`) i sędzia (`judge_findings`): Sonnet 5.5. Fallback przy przeciążeniu lub niedostępności modelu: Sonnet 5.5. To stałe w jednym miejscu (serwis Agenta), nie konfiguracja.
- **Bezpieczeństwo.** Wszystkie nody z modelem mają listę narzędzi tylko do odczytu (`Read`, `Grep`, `Glob`), bez `Bash`, zapisu i sieci. Ograniczenie jest wymuszone trzema opcjami naraz: `tools` (zbiór dostępny), `allowed_tools` (zatwierdzone z góry) i `permission_mode="dontAsk"` (odmowa reszty), bo samo `allowed_tools` niczego nie ukrywa. Sędzia nie ma narzędzi. Treść z PR (kod, spec, tytuł, opis) i Findings pochodzące z niej są danymi, nigdy instrukcjami. Zasady żyją wyłącznie w kodzie tego repozytorium. Wspólne zasady agentów są w małym pliku Markdown w pakiecie (`prompts/rules.md`), który serwis dokleja do `system_prompt`; to odpowiednik CLAUDE.md ładowany przez nas, a nie z repozytorium PR (nazwany inaczej niż `CLAUDE.md`, żeby sesje deweloperskie w tym repo go nie wczytywały). Serwis ma test na opcje przekazane do SDK: lista narzędzi bez zapisujących, `permission_mode` równy `dontAsk`, `setting_sources` puste.
- **Węzły asynchroniczne.** Claude Agent SDK jest asynchroniczny, a `timeout` w `add_node` działa tylko dla nodów async, więc nody z modelem są async i graf jest uruchamiany przez `ainvoke`. Istniejące nody synchroniczne (`collect_input`, `publish`) zostają.
- **Współbieżność i koszty.** `max_concurrency` grafu ograniczone stałą (propozycja: 5). Limitu liczby plików nie wprowadzamy (zgodnie ze spec zbierania Change); ograniczenie kosztu to `max_concurrency`, `timeout-minutes` i `concurrency` z workflow.
- **Strategia retry per node.** Wszystkie nody z modelem mają jedną wspólną politykę `AGENT_RETRY` (`max_attempts=2`, czyli jedno ponowienie, z jitterem), a degradacja po jej wyczerpaniu jest decyzją per node (tabela niżej). Reguły wspólne: (a) klasyfikację błędu robi jeden predykat `is_transient_agent_error` (ten sam wzorzec co `is_transient_git_error`), używany jako `retry_on` przez wszystkie nody z modelem; (b) przejściowe to 429, 5xx i przeciążenie API, błąd połączenia oraz timeout pojedynczej próby; trwałe to 401/403, 400, wyczerpany limit budżetu i błąd w prompcie, które nigdy się nie powiodą; (c) niepoprawny structured output modelu (`InvalidAgentOutput`) jest przejściowy; przy dwóch próbach to automatycznie jedno ponowienie, bo kolejna próba jest tania i często pomaga; timeout noda (`NodeTimeoutError`, który nie dziedziczy po `TimeoutError`) predykat wymienia jawnie; (d) odstępy rosną wykładniczo z jitterem (jitter obowiązkowy, bo workerzy `Send` uderzają równolegle); (e) retry dotyczy wyłącznie zadania, które się nie powiodło: awaria jednego workera `Send` nie powtarza pozostałych; (f) wszystkie nody z modelem są tylko do odczytu, więc ponowienie jest bezpieczne (brak skutków ubocznych).

  | Node | Ponawiane | Próby (propozycja) | Po wyczerpaniu |
  |---|---|---|---|
  | `collect_input` | Konflikt blokady gita (już zrobione) | 3 | Błąd przerywa graf |
  | `review_code` (per plik) | Błędy przejściowe, niepoprawny structured output | 2 | Ostrzeżenie, plik pominięty, reszta idzie dalej |
  | `review_intent` | Jak wyżej, dłuższy timeout (dwa etapy) | 2 | Ostrzeżenie, review bez części "spec" |
  | `validate_findings` | Nic (czysta funkcja) | 1 | Błąd to bug, przerywa graf |
  | `verify_finding` (per Finding) | Błędy przejściowe | 2 | Werdykt `inconclusive` (Finding nie jest tracony) |
  | `judge_findings` | Błędy przejściowe | 2 | Review awaryjne: zwalidowane Findings wg wagi |
  | `nothing_to_review`, `publish` | Błędy przejściowe GitHub API (5xx, timeout, połączenie); upsert jest idempotentny, więc ponowienie jest bezpieczne | 3 | Błąd przerywa graf (czerwony run), nie jest połykany |

- **Budżet czasu a retry.** `RetryPolicy` nie ma globalnego deadline'u, a najgorszy przypadek to liczba prób razy timeout próby, mnożony przez liczbę rund przy `max_concurrency`. Ustalone liczby: timeout próby 2 minuty dla `review_code` i `verify_finding`, `max_attempts=2`, `timeout-minutes` podniesione z 10 do 15 (`PROJECT_GOAL.md`). Najgorszy przypadek jednego noda to 4 minuty; przy `max_concurrency=5` i do 20 weryfikacjach (4 rundy) najgorszego przypadku wszystkich etapów nie da się zmieścić w 15 minutach, więc go nie obiecujemy. Wymagane jest, żeby ścieżka bez awarii (Haiku, kilka plików, kilka minut) mieściła się z zapasem, a obliczenie najgorszego przypadku i jego skutek (runner zabija proces, nic nie jest publikowane) były opisane w komentarzu przy stałych. Timeout `review_intent` (dwa etapy) jest dłuższy i ustala go ticket 06.
- **Warstwy retry nie mogą się mnożyć.** Claude Agent SDK uruchamia Claude Code CLI, który może mieć własne ponawianie błędów API. Przed ustaleniem liczby prób trzeba sprawdzić, co SDK ponawia samo, i nie dokładać tego samego drugi raz w `RetryPolicy` (3 próby SDK razy 3 próby grafu to 9 wywołań, a zegar tyka). Wynik sprawdzenia (w tym wartość i działanie `CLAUDE_CODE_MAX_RETRIES` oraz `API_TIMEOUT_MS`, które CLI czyta ze środowiska) trafia do komentarza przy predykacie; serwis ustawia wybraną wartość jawnie w `env` opcji SDK, żeby nie zależeć od domyślnej.
- **Retry a degradacja.** Kolejność jest stała: najpierw `RetryPolicy`, dopiero po jej wyczerpaniu degradacja z sekcji "Degradacja". Degradacja nigdy nie omija retry.
- **Degradacja.** Błąd workera po wyczerpaniu retry nie może kasować pracy równoległych gałęzi: node zapisuje ostrzeżenie i zwraca pustą listę zamiast przerywać krok. Awaria `judge_findings` daje Review z zwalidowanymi Findings posortowanymi wg wagi, z adnotacją w `summary`. Dokładny mechanizm (łapanie w nodzie vs. obsługa błędu węzła) do wyboru przy implementacji; wymaganie dotyczy zachowania.
- **Komentarz w PR (status i podsumowanie).** Każdy run kończy się komentarzem w rozmowie PR (issue comment), żeby zielony run zawsze miał widoczny wynik: `nothing_to_review` zostawia status "nie ma kodu do sprawdzenia" z liczbami, `publish` status "sprawdzono N plików" z `summary`, także przy zerze Findings ("brak uwag"). Jedna funkcja w `github_io.py` robi upsert: wyszukuje własny komentarz po ukrytym znaczniku w treści oraz autorze będącym botem (sam znacznik nie wystarcza, bo cudzy komentarz z tym tekstem nie może przejąć ani zablokować publikacji), edytuje go albo tworzy nowy. Dzięki temu kolejny push nadpisuje poprzedni wynik, a ponowienie po timeoucie niczego nie dubluje (upsert jest idempotentny). Nadpisanie gubi poprzedni wynik, więc treść zawiera SHA commita i czas. Treść to czysta funkcja renderująca. Cel publikacji (`repo`, `pr_number`, `head_sha`, `dry_run`) wchodzi do stanu jako wejście, tak jak `base_ref` (`head_sha` to ostatni commit gałęzi PR, `github.event.pull_request.head.sha`, a nie `GITHUB_SHA`, który w `pull_request` wskazuje tymczasowy commit scalający); token jest ze zmiennej środowiskowej, nie ze stanu, żeby nie trafiał do strumienia aktualizacji. Bez `dry_run` brak celu lub tokenu to `ValueError` (run czerwony); z `dry_run` komentarz jest drukowany zamiast wysyłany. Błąd publikacji nie jest połykany. Zweryfikowane w dokumentacji REST API: komentarze rozmowy PR i pojedyncze komentarze przy linii można listować, edytować i usuwać, treść wysłanego Review można zmienić, ale samego wysłanego Review nie można usunąć, a dokumentacja nie mówi, czy Review typu `COMMENT` da się odrzucić. Dlatego nadpisywanie dotyczy tylko komentarza ze statusem; komentarze przy liniach i ich "powłoki" są sprawą osobnej specyfikacji `publish`.
- **Dokumentacja.** Po wdrożeniu poprawić: `PROJECT_GOAL.md` (drzewo modułów bez `run_agent`, zamknięta decyzja nr 3, opis przepływu), `CONTEXT.md` (nowe terminy: Candidate, Verdict, Judge oraz rozszerzony Finding), `LEARNING_GOAL.md` bez zmian.

## Testing Decisions

- **Dobry test** sprawdza zachowanie widoczne z zewnątrz: które nody się wykonały i ile razy, jakie Findings i `summary` są w stanie końcowym, kiedy graf kończy się wcześnie. Nie sprawdza treści promptów, kolejności wywołań wewnętrznych funkcji ani sposobu parsowania.
- **Seam 1, najwyższy i istniejący: `ainvoke`/`stream` skompilowanego grafu** na tymczasowym repozytorium git, z atrapą modelu na granicy wykonania Agenta. Obserwacja przez `stream_mode="updates"`. Scenariusze: PR bez plików kodu (tylko dokumentacja, lockfile lub Intent files) wykonuje wyłącznie `collect_input` i `nothing_to_review`, drukuje komunikat, zleca jeden upsert komentarza ze statusem i nie uruchamia żadnego node z modelem; PR z N plikami kodu daje N wykonań `review_code`; z Intent files daje jedno `review_intent`, bez nich zero; brak Findings po walidacji pomija `verify_finding` i `judge_findings`; M Findings daje M weryfikacji (do limitu); awaria jednego workera zostawia pozostałe wyniki i ostrzeżenie; awaria sędziego daje Review awaryjne.
- **Seam 2, nowy, konieczny: granica wykonania Agenta.** Jedno miejsce podmieniane w testach (jak dziś podmieniane jest `collect_change`), z kanonicznymi odpowiedziami per rola i błędami przejściowymi lub trwałymi. Sam serwis ma osobny, wąski test z podmienionym `query` z SDK, który sprawdza przekazane opcje (narzędzia, tryb uprawnień, `setting_sources`, fallback). Dzięki temu żaden test nie woła prawdziwego modelu.
- **Seam 3: interfejsy czystych funkcji**: walidacja Findings (tabela przypadków: plik spoza zmiany, linia poza plikiem, cytat nieobecny, brak `spec_ref`, duplikat) stosowanie decyzji sędziego (odrzuć, scal, zmień wagę, nieznane `id`, próba dopisania) oraz renderowanie komentarza ze statusem (warianty: brak kodu, sprawdzono N plików, brak uwag).
- **Seam 4, nowy, konieczny: granica GitHub** (upsert komentarza w `github_io.py`), podmieniana w testach tak jak granica Agenta. Bez niej nie da się sprawdzić, że drugi run edytuje komentarz, a cudzy komentarz ze znacznikiem nie jest nadpisywany. Treść komentarza to czysta funkcja i wchodzi do Seam 3.
- **Testy retry** na Seam 1, bez realnego czekania (prior art: `COLLECT_INPUT_RETRY` z `initial_interval=0` i `jitter=False` w `tests/test_graph.py`). Scenariusze dla każdego noda z modelem: błąd przejściowy potem sukces daje dokładnie 2 wywołania granicy; błąd trwały daje 1 wywołanie; wyczerpanie prób uruchamia degradację właściwą dla noda (tabela wyżej); awaria jednego workera `Send` nie zwiększa liczby wywołań pozostałych (liczone per plik lub per Finding). Osobno tabela klasyfikacji błędów granicy (przejściowy vs trwały), jak `test_collect_input.py`.
- **Test jednego wywołania z prawdziwym modelem**: opcjonalny, pomijany bez `ANTHROPIC_API_KEY` w środowisku, oznaczony jako integracyjny i niewchodzący w domyślny przebieg.
- **Prior art.** `tests/test_graph.py` (wywołanie `build_graph()` na repo z `tmp_path` i monkeypatch na punkcie granicznym), `tests/test_collect_input.py` (tabela predykatu `retry_on`), `tests/test_change.py` (czyste funkcje na fixture'ach).
- Dotychczasowe testy grafu, które asercją sprawdzały wydruk `run_agent`/`publish`, trzeba zmienić na asercje na `stream_mode="updates"` i `ainvoke`. Po dodaniu komentarza w PR przekazują one `dry_run` albo atrapę granicy GitHub.

## Out of Scope

- Review z komentarzami przy liniach i Pull Request Reviews API (osobna specyfikacja `publish`), w tym jego strategia retry. Uwaga na przyszłość: wysłane Review nie jest idempotentne ani usuwalne, więc ponowienie po timeoucie może zdublować Review, a nadpisanie poprzednich komentarzy przy liniach zostawia puste "powłoki" Review. Wymaga to osobnej decyzji, w tym sprawdzenia, czy Review typu `COMMENT` da się odrzucić. Komentarz ze statusem i podsumowaniem jest w zakresie.
- PR z forka: `GITHUB_TOKEN` jest tam tylko do odczytu, więc publikacja się nie uda (run czerwony). Obsługa forków jest osobną sprawą.
- Punkt wejścia CLI (w tym flaga `--dry-run` i wypełnianie wejść z kontekstu Actions), wczytywanie `.env`, `action.yml`, workflow w Actions. Sam tryb `dry_run` publikacji (drukuj zamiast wysyłać) jest w zakresie.
- Pętla evaluator-optimizer (sędzia odsyłający Findings do ponownego recenzowania). W v1 sędzia robi jeden przebieg.
- Checkpointer, interrupt, subgraphy, LangSmith, cache nodów.
- Reguły i konfiguracja per repozytorium.
- Porównywanie z poprzednimi review tego samego PR (deduplikacja między uruchomieniami `synchronize`).
- Ocena zgodności między plikami spoza `change["code"]`; recenzent czyta kontekst narzędziami, ale nie recenzuje niezmienionego kodu.
- Limit liczby lub rozmiaru plików (dodamy, gdy prawdziwy PR go przekroczy).
- Pomiar i budżet tokenów.

## Further Notes

- **Kolejność dostarczania (wejście do rozbicia na tickety).** Po każdym kroku graf działa od START do END, a nody jeszcze niewykonane zostają stubami z kroku 3. (1) Wyjście bez kodu: `collect_input` zwraca `Command`, a nowy node `nothing_to_review` wypisuje informację i kończy graf. (2) Komentarz w PR ze statusem i podsumowaniem: upsert w `github_io.py`, używany przez `nothing_to_review` i `publish`, z `dry_run` i własnym `RetryPolicy`. (3) Szkielet grafu: puste nody, topologia (`Send` per plik i per Finding, routing, reducery), stubowe nody zwracają stały wynik, `validate_findings` jest przepuszczalnikiem; testy topologii. (4) Serwis Agenta (`run_agent`, wspólne domyślne, plik reguł), predykat `is_transient_agent_error` ze wspólną polityką `AGENT_RETRY`, timeout na nodzie, spike sprawdzający retry wewnątrz SDK i prawdziwy `review_code` per plik. (5) `validate_findings`. (6) `review_intent` z `AGENT_RETRY`. (7) `verify_finding` z `AGENT_RETRY` i degradacją do `inconclusive`. (8) `judge_findings` z `AGENT_RETRY` i Review awaryjnym. (9) Degradacja pozostałych nodów (ostrzeżenia, pominięty plik), `max_concurrency`, policzony budżet czasu i dokumentacja. Zasada: każdy node z modelem dostaje `AGENT_RETRY` i timeout w tym samym tickecie, w którym staje się prawdziwy, a nie dopiero na końcu.
- **Stuby z kroku 3** zwracają: `review_code` jedną zakotwiczoną uwagę na pierwszą linię pliku, `review_intent` jedną uwagę ogólną, `verify_finding` werdykt `confirmed`, `judge_findings` zostawia wszystko i ustawia `summary` na stały tekst. Dzięki temu każda gałąź topologii jest wykonywana już w kroku 3.
- **Rozstrzygnięte:** PR bez żadnych Findings dostaje komentarz ze statusem "brak uwag" i liczbą sprawdzonych plików, nie ciszę. Powód: zielony run bez śladu w PR wygląda jak awaria agenta.
- **Kompromis `Send` per plik:** równoległość i prosty model mentalny kosztem uwag przekrojowych (zależności między plikami). Częściowo łagodzi to narzędzie do odczytu repozytorium w każdym workerze oraz `review_intent`, który widzi całą zmianę. Jeśli w praktyce zbyt dużo przekrojowych błędów ucieka, kolejnym krokiem jest grupowanie plików, nie zmiana wzorca.
- **Kandydat na ADR:** płaski graf i brak subagentów SDK (decyzja o roli SDK w grafie), bo zamyka otwartą decyzję projektu i jest kosztowna do odwrócenia.
- **Uwaga do testu z prawdziwym modelem:** `.env` nie jest wczytywany automatycznie; klucz trzeba wyeksportować lub uruchomić test przez `uv run --env-file .env`.
- **Zmiana wobec specyfikacji zbierania Change.** Tamta specyfikacja (`.scratch/change-collection/spec.md`) ustaliła wyjście przy pustym `code` jako krawędź warunkowa do END, widoczną w grafie. Ta specyfikacja ją zastępuje: wyjście przechodzi do `Command` w `collect_input` i node `nothing_to_review`. Zysk: jawny, nazwany stan końcowy z komunikatem. Koszt: routing jest w node, nie w definicji grafu, a `collect_input` zna nazwy kolejnych nodów. Jeśli to zacznie przeszkadzać przy fan-oucie, alternatywą jest cienki node `plan_review` między `collect_input` a recenzentami; wtedy `collect_input` kieruje tylko do `plan_review` albo `nothing_to_review`.
- **Rozdzielenie `publish`.** Komentarz ze statusem (krok 2) jest tu, a Review z komentarzami przy liniach zostaje w osobnej specyfikacji. Jedna funkcja upsert służy obu nodom kończącym, więc jest jedną granicą GitHub, nie dwiema.
- **Powiązanie z nauką:** reducery i `Send` (kroki 3 z `LEARNING_GOAL.md`), structured output (krok 2), streaming `updates` w testach (krok 4), `RetryPolicy` (krok 5), `ainvoke` (koncept compile/invoke/ainvoke).
- **Bez `Bash`:** agent nie ma `git diff`, `git log` ani `git show`. Diff pliku (i w razie potrzeby historia) dostarcza node w prompcie jako dane. Zysk: znika cała klasa ryzyka z ograniczaniem poleceń powłoki. Koszt: agent sam nie sprawdzi historii zmian.
- **Zasięg `Read` i sekrety na runnerze (poza zakresem).** `Read` nie jest ograniczony do `cwd`, a `actions/checkout` domyślnie zostawia token w `.git/config`. Prompt injection w PR mogłoby więc dostać token w cytacie (`evidence`) opublikowanym w komentarzu. Zmniejszenie ryzyka (`persist-credentials: false` w workflow docelowego repo, ograniczenie ścieżek `Read` przez reguły uprawnień) to osobna decyzja, nie ticket 04.
- **Wyniki spike'a SDK (ticket 04).** `Bash` i `Write` nie są w ogóle oferowane przy `tools=[Read,Glob,Grep]` (lista narzędzi w `init`), a `tools=[]` daje tylko `StructuredOutput`. Błąd połączenia przychodzi jako `ResultError` z `api_error_status=None` i `terminal_reason="api_error"`, zły klucz jako `ResultError` 401 z `subtype="success"`, a limit tur jako `error_max_turns`. Domyślne ponawianie CLI przy błędzie połączenia trwało ponad 150 s (`CLAUDE_CODE_MAX_RETRIES=0`: 1,1 s, `1`: 1,5 s), więc serwis ustawia je jawnie. Anulowanie zapytania kończy podproces CLI od razu.
- **Plik reguł a CLAUDE.md:** `setting_sources=[]` blokuje wszystkie CLAUDE.md i `.claude/` (także z repozytorium autora PR, który mógłby wpłynąć na recenzenta). Wspólne zasady idą własnym plikiem doklejanym do `system_prompt`; w SDK CLAUDE.md jest ładowany wyłącznie przez `setting_sources`, więc to nie jest ten sam mechanizm, tylko ten sam efekt.
- **Zmiana modeli i retry wobec pierwszej wersji spec:** recenzenci na Haiku, weryfikator i sędzia na Sonnet; jedna polityka `AGENT_RETRY` zamiast osobnej per node; timeout na nodzie; serwis bez własnej hierarchii wyjątków.
